# Pull Request 생성 Skill

현재 브랜치의 전체 변경사항을 분석하고, 구조화된 PR을 GitHub에 생성합니다.

## 사전 확인

1. 현재 디렉토리가 git 저장소인지 확인합니다.
2. `gh` CLI가 설치되어 있고 인증되어 있는지 확인합니다.
3. 현재 브랜치가 `main` 또는 `master`가 아닌지 확인합니다.
- 기본 브랜치라면 "PR을 생성할 피처 브랜치에서 실행해주세요"라고 안내합니다.
4. 리모트에 push되지 않은 커밋이 있는지 확인합니다.
- 있으면 push할지 사용자에게 확인 후 `git push -u origin <branch>` 를 실행합니다.

    ## 변경사항 분석

    ### 1단계: 브랜치 정보 파악

    ```bash
    git branch --show-current
    git log --oneline main..HEAD    # 또는 master..HEAD
    git diff --stat main..HEAD
    ```

    다음을 파악합니다:
    - 현재 브랜치 이름
    - base 브랜치 대비 커밋 수
    - 변경된 파일 수와 추가/삭제 라인 수

    ### 2단계: 커밋 히스토리 분석

    ```bash
    git log --format="%s%n%b---" main..HEAD
    ```

    각 커밋 메시지를 읽고 전체 작업의 맥락을 이해합니다.

    ### 3단계: 코드 변경 상세 확인

    ```bash
    git diff main..HEAD
    ```

    변경의 성격과 영향 범위를 파악합니다.

    ## PR 메시지 작성

    ### 제목 형식

    ```
    type(scope): 한 줄 요약
    ```

    - 커밋과 동일한 type/scope 컨벤션을 따릅니다.
    - 여러 type에 걸치면 가장 핵심적인 것을 선택합니다.
    - 브랜치명에 이슈 번호가 있으면 (예: `feat/12-login`) 참조를 포함합니다.

    ### 본문 템플릿

    ```markdown
    ## 📋 개요
    <!-- 이 PR이 무엇을 하는지 2-3문장으로 요약 -->

    ## 🎯 관련 이슈
    <!-- closes 키워드로 이슈 자동 종료 -->
    - closes #이슈번호

    ## 🔄 변경 사항

    ### Why
    - (왜 이 변경이 필요한가?)

    ### What
    - (무엇이 어떻게 바뀌었나?)

    ### How
    - (기술적으로 어떤 접근 방식을 선택했는가?)

    ## 📸 스크린샷 / 데모
    <!-- UI 변경이 있으면 스크린샷을 첨부하세요 -->
    <!-- 해당 없으면 이 섹션 삭제 -->

    ## ✅ 체크리스트
    - [ ] 코드가 정상 동작하는지 확인
    - [ ] 린트/타입체크 통과 확인
    - [ ] 관련 이슈에 연결됨
    - [ ] 팀원 리뷰 요청

    ## 🧪 테스트 방법
    <!-- 리뷰어가 이 PR을 어떻게 테스트할 수 있는지 -->
    1. `단계 1`
    2. `단계 2`
    3. 예상 결과: ...

    ## 🤖 AI 사용 내역
    <!-- 해커톤 공정성을 위한 투명한 기록 -->
    - (AI 도구를 사용했다면: 무엇을 위임했고, 무엇을 직접 검증했나?)
    ```

    ## 라벨 자동 지정

    변경 내용에 따라 라벨을 자동 지정합니다:

    | 조건 | 라벨 |
    |------|------|
    | type이 `feat` | `feature` |
    | type이 `fix` | `bug` |
    | type이 `docs` | `documentation` |
    | type이 `refactor` | `refactor` |
    | type이 `infra`/`chore`/`ci` | `infra` |
    | 변경 파일 < 5개 | `size: S` |
    | 변경 파일 5-15개 | `size: M` |
    | 변경 파일 > 15개 | `size: L` |

    리포지토리에 라벨이 없으면 `gh label create`로 생성합니다.

    ## 이슈 자동 연결

    다음 순서로 관련 이슈를 탐지합니다:

    1. **브랜치명에서 추출**: `feat/12-login` → `#12`
    2. **커밋 메시지에서 추출**: `Refs: #12` 또는 `#12` 패턴
    3. **사용자 인자에서 추출**: `/create-pr #12`
    4. **탐지 실패 시**: 사용자에게 관련 이슈 번호를 질문

    연결된 이슈는 본문에 `closes #번호`로 삽입하여 머지 시 자동 종료되게 합니다.

    ## 실행 절차

    1. 브랜치 정보와 변경사항을 분석합니다.
    2. PR 제목과 본문 초안을 사용자에게 보여줍니다.
    3. 사용자가 확인하면 (또는 수정 요청을 반영한 후) PR을 생성합니다.

    ```bash
    # push되지 않은 커밋이 있으면
    git push -u origin <current-branch>

        # PR 생성
        gh pr create \
        --title "type(scope): 한 줄 요약" \
        --body "본문 내용" \
        --base main \
        --label "라벨1,라벨2" \
        --assignee "@me" \
        --reviewer "리뷰어"
        ```

        4. 생성된 PR URL을 사용자에게 보여줍니다.

        ## 인자 처리

        - `/create-pr` — 변경사항 분석 후 PR 자동 생성
        - `/create-pr #12` — 이슈 #12와 연결하여 PR 생성
        - `/create-pr --reviewer @teammate` — 특정 리뷰어 지정
        - `/create-pr --draft` — Draft PR로 생성 (작업 진행 중 공유용)

        ## 예시

        ### 입력
        ```
        /create-pr
        ```

        ### 출력 (사용자 확인용 초안)

        **제목**: `feat(auth): 카카오 소셜 로그인 구현`

        **본문**:
        ```
        ## 📋 개요
        카카오 OAuth2를 이용한 소셜 로그인 기능을 구현했습니다.
        로그인 성공 시 JWT 토큰을 발급하고 세션을 관리합니다.

        ## 🎯 관련 이슈
        - closes #12

        ## 🔄 변경 사항

        ### Why
        - 해커톤 MVP에서 간편 로그인이 핵심 요구사항
        - 별도 회원가입 없이 빠른 온보딩 필요

        ### What
        - KakaoStrategy OAuth2 인증 플로우 추가
        - /api/auth/kakao 콜백 엔드포인트 구현
        - JWT 토큰 발급 및 리프레시 로직 적용

        ### How
        - Passport.js 기반 카카오 전략 패턴 적용
        - 토큰은 httpOnly 쿠키로 관리하여 XSS 방어

        ## ✅ 체크리스트
        - [x] 코드가 정상 동작하는지 확인
        - [x] 린트/타입체크 통과 확인
        - [x] 관련 이슈에 연결됨
        - [ ] 팀원 리뷰 요청

        ## 🧪 테스트 방법
        1. /login 페이지에서 "카카오로 로그인" 클릭
        2. 카카오 인증 완료 후 리다이렉트 확인
        3. 예상 결과: 메인 페이지로 이동, 우측 상단에 프로필 표시

        ## 🤖 AI 사용 내역
        - Claude Code로 KakaoStrategy 보일러플레이트 및 콜백 핸들러 생성
        - JWT 발급 로직, 에러 핸들링, 쿠키 설정은 직접 작성 및 검증
        ```

        **라벨**: `feature`, `size: S`
        **담당자**: `@me`

        > 이대로 PR을 생성할까요? (수정할 부분이 있으면 말씀해주세요)

        ## 주의사항

        - PR 본문은 반드시 사용자에게 보여주고 확인을 받은 후 생성합니다.
        - base 브랜치가 `main`이 아닌 경우 (예: `develop`) 사용자에게 확인합니다.
        - 커밋이 1개뿐이면 해당 커밋 메시지를 PR 본문의 기반으로 활용합니다.
        - 변경이 매우 크면 (20개 파일 이상) PR 분리를 제안합니다.
        - AI 사용 내역은 해커톤 공정성 가이드에 따라 솔직하게 기록합니다.
